---
title: Validation
description: Cadence renders invalid state; it never decides what is invalid.
---

## The rule

Components ship the UI for an invalid state and nothing else. They do not own schemas, rules,
form state, or submission. If a component ever needs to know *why* a value is invalid, that logic
belongs in your application code.

This is why there is no `form` component in the registry: a form wrapper is a validation
integration, not a visual primitive.

## What the component does

- Styles the invalid state from an attribute, not from internal state: `aria-invalid="true"`
  turns the border and ring destructive.
- Renders the error slot you give it (`FieldError`, or any element inside `Field`), and marks it
  `role="alert"` so the message is announced when it appears.
- Leaves the id graph to you: the component renders the element, you put its `id` on the slot and
  point the control's `aria-describedby` at it. Nothing is generated, so nothing can guess wrong.
- Passes `disabled`, `required`, and `readOnly` through to the underlying control.
- Keeps focus visible and the control keyboard reachable in every state.

## What you do

- Decide validity: required, format, length, async uniqueness.
- Wire `aria-invalid` on the control and `aria-describedby` at the error element's `id` — see
  [Field](/components/field) for the pairing.
- Provide the resolver or schema (zod, valibot, yup) and the form state library
  (react-hook-form, TanStack Form).
- Submit, retry, and map server errors back to fields.
- Decide where focus goes after a failed submit.

## Wiring it by hand

```tsx
const [error, setError] = useState<string | null>(null);

<form
  onSubmit={(event) => {
    event.preventDefault();
    const value = new FormData(event.currentTarget).get("email");
    setError(typeof value === "string" && value.includes("@") ? null : "Enter a valid email address.");
  }}
>
  <Field data-invalid={error ? true : undefined}>
    <Label htmlFor="email">Email</Label>
    <Input id="email" name="email" aria-invalid={error ? true : undefined} aria-describedby="email-error" />
    {error ? <FieldError id="email-error">{error}</FieldError> : null}
  </Field>
  <Button type="submit">Save</Button>
</form>
```

Nothing in that snippet is provided by Cadence except the visual components. The condition, the
message, and the decision to show it are yours.

## With a form library

```tsx
const form = useForm({ resolver: zodResolver(schema) });

<Field data-invalid={form.formState.errors.email ? true : undefined}>
  <Label htmlFor="email">Email</Label>
  <Input id="email" aria-invalid={form.formState.errors.email ? true : undefined} {...form.register("email")} />
  <FieldError>{form.formState.errors.email?.message}</FieldError>
</Field>
```

The library owns the state; the component only reflects it.

## Why this boundary

1. **No lock-in.** Swapping react-hook-form for TanStack Form does not touch the component.
2. **No duplication.** Two validation owners produce two sources of truth and contradictory errors.
3. **Testable.** The contract is an attribute: given `aria-invalid`, the visual and semantic state
   must be correct. No mocks, no schema fixtures.
4. **Smaller payloads.** No schema library enters the registry dependency graph.

`pnpm registry:check` fails if a component imports a validation library or declares one as a
dependency.
